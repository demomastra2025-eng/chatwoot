# Картинки клиентов: описание при получении, роутер и два чтеца

Решения владельца: 07.10 (агент видит только текст картинки), 27.10 («Хорошо. Согласен.» на роутер и двух чтецов).
Код: `Captain::ImageRecognitionService` (кеш и «один вызов на картинку»), `Captain::ImageReading::{Picture, Router, Reader, Prompt}`,
`Messages::ImageDescriptionJob` (описание при получении), `Captain::OpenAiMessageBuilderService` (что видит агент).

## 1. Как это работает

1. Картинка пришла в диалог агента: `Messages::ImageDescriptionJob` описывает её в фоне. Подсказка или живой ответ находят текст в
   `attachments.meta` и не ждут. Если текста ещё нет, запуск описывает картинку сам, один раз (замок в Redis: два вызова на одну картинку не идут).
2. Картинка читается один раз: оригинал берётся из хранилища (внешняя ссылка канала, если файла нет, идёт через `SafeFetch`). Длинная
   сторона больше 1536 px: ужимается до 1536 в JPEG (libvips, качество 85); не больше 1536 px и тип jpeg/png/webp: уходит как есть.
3. Роутер (модель решений, картинка 1024 px JPEG data-URL в состоянии) отвечает на один вопрос: написано ли на картинке что-нибудь от
   руки (в том числе печатная форма, заполненная рукой). P(рукописный) не ниже 0.3 или роутер не ответил: читает модель рукописного
   текста. Иначе обычная модель. Формулировка вопроса и порог 0.3 измерены вместе (PROD 27.10, в памяти, 81 картинка бенчмарка, из них
   16 с рукописью, запрос ровно такой, какой шлёт `Captain::ImageReading::Router`, два прогона): P(рукописный) у всех 16 от 0.56 до 1.00,
   то есть при 0.3 все 16 уходят к Terra (запас 0.26), из остальных 65 туда уходят 6 (9%). Первая формулировка («значимый рукописный
   текст») давала 0.06 и 0.28 на двух печатных бланках, заполненных рукой, и теряла их (14/16). Менять формулировку или порог только вместе
   с новым замером (пример в `router_spec` закрепляет текущие).
4. Чтец получает универсальную инструкцию (без слов про отрасль; строка «Сфера компании: …» берётся из `accounts.custom_attributes['industry']`,
   если она заполнена) и картинку данными в запросе, не ссылкой. Ответ до 4000 токенов (запас на рассуждение Terra и длинную страницу); температура 0 только
   там, где модель её принимает. Если ответ обрезан лимитом (`finish_reason = length`), в конце текста стоит «[…текст обрезан]»,
   чтобы агент не принял его за весь текст.
5. Текст и чтец сохраняются в `attachments.meta`: `image_recognition_description`, `image_recognition_reader` (`ordinary` или
   `handwriting`), `image_recognition_model`. Неудачное чтение запоминается в `image_recognition_failures` (`count`, `at`, `error`: только
   класс ошибки): после двух неудач подряд новых вызовов нет 3 часа, агент сразу получает «распознавание недоступно». Ошибки платформы
   (ключ, нет модели) на картинку не записываются. Удачное чтение стирает отметку. Замок «один вызов на картинку» держится 150 с.
6. Агент (подсказка, живой запуск, консилиум, рассылки) **никогда** не получает картинку: ни пикселей, ни ссылки. Он видит только
   «Image attachment (automatic description, it may be inaccurate): …». Текст картинок в истории идёт через свой бюджет (8 КБ на все
   картинки истории, отдельно от 16 КБ текста диалога): самая новая картинка получает текст целиком, более старая остаток с пометкой
   «[…]», самая старая, когда места нет, строку «its description is left out». Диалог картинками не вытесняется.
7. Картинка до 1536 px уходит как есть только если в файле нет метаданных (EXIF, XMP, IPTC) и нет поворота; иначе файл пересобирается
   в JPEG: повернут, без метаданных (место и время съёмки провайдеру не нужны). Картинка больше 100 мегапикселей не читается.
8. Инструмент `faq_lookup` привязан к агенту, у которого есть что искать: одобренная запись FAQ или фрагмент документа, которые он видит
   (поиск по словам документов тоже в `faq_lookup`).

## 2. Настройки (Super Admin, «Модели ИИ», группа «Картинки»), одинаковые для всех аккаунтов

| Строка | Что | Пусто значит |
|---|---|---|
| `CAPTAIN_IMAGE_RECOGNITION_MODEL` | обычный чтец | `google/gemini-3.1-flash-lite` |
| `CAPTAIN_IMAGE_HANDWRITING_MODEL` | чтец рукописного текста (и при ошибке роутера) | `openai/gpt-6.1-terra` |
| `CAPTAIN_IMAGE_ROUTER_MODEL` | модель решений роутера | `perplexity/pplx-decider-v1.2` |

Эти функции больше не идут за `CAPTAIN_DEFAULT_MODEL` (Luna): смена модели агента не двигает чтение картинок. Моделей-запасных нет.
Модель вне Google / OpenAI / Perplexity форма не примет, а если её всё же записали, запрос не строится (картинка получит текст
«распознавание недоступно»).

Провайдеры OpenRouter (`provider.only`): Gemini: `google-vertex`, `google-ai-studio`; Terra и другие OpenAI: `openai`, `azure`;
роутер: `perplexity`. Остальное (`data_collection: deny`) как у всех запросов.

## 3. Журнал

Одна строка `llm_events` на чтение картинки: `event_name = 'captain.image.read'`, `feature = 'image_recognition'`, `model` (чтец),
`duration_ms` (всё чтение), в `payload`: `reader`, `reader_ms`, `router_status` (`ok`/`failed`), `router_model`, `router_choice`,
`router_probability`, `router_ms`, `router_error_class`, `finish_reason` (`stop` или `length`), `reader_usage` (`input_tokens`, `output_tokens`), `router_cost` (по ответу
провайдера), `reader_cost` (оценка по цене из каталога, пусто, пока в каталоге нет цены модели), `total_cost`. Токены и доллары лежат
только в `payload` (токены вложенным объектом: журнал закрывает ключ со словом token), не в колонках `prompt_tokens`/`estimated_cost`: их суммируют панели, а вызовы уже посчитаны на своих строках
(`llm.decision.complete` с `feature = 'image_routing'` для роутера и обычное событие чата с `feature = 'image_recognition'` для чтеца),
вторая запись тех же долларов удвоила бы расход на картинки. Картинок, ссылок на них и прочитанного текста в событиях нет.

```sql
-- доля картинок по чтецам и задержка за сутки
SELECT payload->>'reader' AS reader, count(*), round(avg(duration_ms)) AS avg_ms,
       count(*) FILTER (WHERE payload->>'router_status' = 'failed') AS router_failed
FROM llm_events WHERE event_name = 'captain.image.read' AND created_at > now() - interval '1 day' GROUP BY 1;
```

## 4. Откат

Только данные, кода менять не нужно: в Super Admin поставить `CAPTAIN_IMAGE_RECOGNITION_MODEL` и `CAPTAIN_IMAGE_HANDWRITING_MODEL` на
`openai/gpt-6-luna` (роутер при этом всё равно вызывается; чтобы не платить за него, оба чтеца можно сделать одинаковыми, роутер дешёвый:
$0.02 за 1000 картинок). Описание при получении выключает переменная `CAPTAIN_IMAGE_DESCRIPTION_ON_ARRIVAL=off`.

## 5. Шаг данных при выкладке: старые описания (необязательный)

В PROD около 125 описаний сделаны старым промптом («опиши для сотрудника поддержки»): он выдумывает детали на рукописи и мелком шрифте, а
агент больше не видит пиксели, чтобы проверить. У них нет отметки `image_recognition_reader`. Шаг стирает такое описание у картинки, которую
можно прочитать заново (файл в хранилище или внешняя ссылка, не удалён), и следующий запуск читает её новым конвейером один раз
(около $0.001-0.007 за картинку). Описание картинки, которой уже нет, остаётся: другого текста нет.

```
# 1. сухой прогон: только счётчики
bundle exec rails onelink:captain:legacy_image_descriptions
# 2. применить: сначала файл копии (0600) в BACKUP_DIR, на постоянном томе, не в /app/tmp
APPLY=1 CONFIRM=yes BACKUP_DIR=/app/storage/onelink_backups/<rel> bundle exec rails onelink:captain:legacy_image_descriptions
# 3. повторный сухой прогон: to_forget = 0
# откат: вернуть описания из копии туда, где у картинки сейчас нет описания
RESTORE=/app/storage/onelink_backups/<rel>/legacy-image-descriptions-<время>.json CONFIRM=yes bundle exec rails onelink:captain:legacy_image_descriptions
```
Счётчики сухого прогона должны быть около 125 (`legacy`) и чуть меньше (`to_forget`); сильно другие числа: остановиться и разобраться.
