# Переключение учёта отправленных AI-ответов

Этот runbook относится к `Accounts::AiUsageOutbox`, миграциям
`20261102013000`, `20261102013100` и `20261102013200`. Команды выполняет релизный агент на
разрешённом стенде. Для PROD нужно отдельное разрешение владельца на релиз.
Нельзя включать старый и новый механизмы начисления одновременно.

## 1. Схема

Схему и prepare запускать одноразовым maintenance-процессом нового образа,
не переключая live AI writers на этом шаге. Применить все три миграции до запуска
новой версии приложения. Первая содержит
только короткий DDL (`lock_timeout = 5s`), без исторического INSERT. Вторая
создаёт partial index `idx_messages_pending_ai_usage` через `CONCURRENTLY`,
в отдельной миграции без DDL-транзакции. Для большого индекса отдельно задать
разумный `POSTGRES_STATEMENT_TIMEOUT` maintenance-команды; короткий DDL
сохраняет `lock_timeout = 5s`. Не использовать общий внешний
transaction wrapper. Если concurrent build прервался, повторный `up` удаляет
его невалидный индекс и строит заново.

Проверить колонки `messages.ai_usage_version`, `ai_usage_sent_at`,
`ai_usage_pending`, `ai_usage_retry_at`, таблицы `account_ai_usage_events`,
`account_ai_dialog_states`, `account_ai_usage_rollouts` и валидность индекса.
Третья миграция создаёт пустую таблицу `captain_reply_suggestion_identities` и
уникальный индекс `idx_reply_suggestion_identity_request`; только короткий DDL
с `lock_timeout = 5s`, без backfill. Состояние rollout изначально неактивно. Миграция не списывает исторический расход.

## 2. Подготовка истории

```sh
bundle exec rake accounts:ai_usage:prepare
```

`prepare` фиксирует high-water ID и сохраняет cursor после каждой транзакции
из максимум 1000 сообщений. Чтение `messages` не берёт row locks. INSERT
исторических source keys и cursor коммитятся вместе. Прерывание и повтор
безопасны; `ON CONFLICT` не повторяет запись. Счётчики аккаунтов не меняются. Полный preflight выполняется в пункте 4,
после регистрации нового recovery worker.
Это длительная операция вне DDL-блокировки; её стоимость на PROD сначала
измеряется отдельно. Вывод содержит только готовность и cursor/cutoff, без текстов.

Новые публичные исходящие, созданные новым кодом, имеют `ai_usage_version=1`.
Их pending-начисления не поглощаются историческим backfill даже до активации.
У старых сообщений версия NULL: поздний ack/feedback сохраняет их историческими
и не начисляет расход повторно, даже если ack появился после прохода cursor.
Повтор `prepare` после подготовки/активации не передвигает cutoff и не обнуляет
новые события. Старые ID остаются в журнале после закрытия окон и смены месяцев.

## 3. Drain старых writers и смена кода

До допуска новых AI-generating writers остановить приём новых задач старым
механизмом и дождаться окончания уже выполняемых задач. Проверить все Rails/
Captain/follow-up workers по SHA: старый код вызывает прямое начисление при
создании ответа и не должен работать одновременно с новым механизмом.
Обычную переписку и подтверждённые provider IDs не очищать и не переотправлять.

Развернуть новый код с ещё неактивным rollout. До активации ack и PostgreSQL
pending уже сохраняются, но счётчики сообщений не меняются. Не полагаться на
безопасность произвольного rolling-переключения старых AI writers: drain —
отдельные обязательные ворота. Релизный агент проверяет их факт перед
передачей `AI_USAGE_LEGACY_WRITERS_DRAINED=1`.

## 4. Активация

Проверить, что новый Sidekiq schedule содержит активный
`drain_ai_usage_job` (`Accounts::DrainAiUsageJob`, `scheduled_jobs`,
`17 * * * * *`, `active_job: true`). Это 17-я секунда каждой минуты, отдельно
от шторма `:00`. Сверить регистрацию задания в Sidekiq Cron и версию воркера.

```sh
bundle exec rake accounts:ai_usage:preflight
AI_USAGE_LEGACY_WRITERS_DRAINED=1 bundle exec rake accounts:ai_usage:activate
bundle exec rake accounts:ai_usage:preflight
```

Activation откажет без завершённого prepare, валидных pending/identity индексов,
зарегистрированного enabled cron с нужным классом/расписанием и явного
подтверждения drain. Повтор activation не меняет уже активное состояние.
Затем проверить уменьшение числа pending и однократный ledger event на
согласованном тестовом сообщении. Внешние тестовые отправки — только в рамках
отдельно согласованной проверки владельца.

Ack и pending сохраняются в одной транзакции Message. Начисление выполняется
после commit в отдельной транзакции; сбой оставляет pending. Redis enqueue не
требуется для сохранности события. Cron обрабатывает максимум 200 due rows за
проход по индексу `(ai_usage_retry_at, id) WHERE ai_usage_pending`; занятая другим
reconciler строка пропускается через `FOR UPDATE SKIP LOCKED`; ошибка
сдвигает строку на минуту, позволяя следующим строкам попасть в следующий batch.
Повтор не вызывает channel send service. Ledger, окно, monthly delta и снятие
pending коммитятся вместе. При недоступной очереди pending остаётся в PostgreSQL
до восстановления scheduled worker. Идентификаторы провайдера не откатываются
ошибкой счётчика. Сохранение самого ack по-прежнему требует доступной БД messages.

## 5. Pause и rollback

```sh
bundle exec rake accounts:ai_usage:pause
bundle exec rake accounts:ai_usage:preflight
```

Pause отключает reconciler, сохраняя ack, provenance, source history и pending.
Уже начатая транзакция может завершиться; дождаться её окончания. После
исправления причины повторить preflight и activation — подготовка истории и
старые события не переоплачиваются.

До активации откат кода допустим при остановленных новых billable writers;
не удалять pending новых сообщений, они должны быть разобраны новым reconciler.
После активации штатный безопасный откат metering — pause и исправление вперёд
с сохранением схемы/журнала. Не возвращать старую прямую тарификацию поверх
уже учтённых новых окон и не выполнять `db:rollback` на активных данных.
Если нужен откат всего приложения, сначала отдельно согласовать остановку
billable AI writers и сохранение нового reconciler для накопленного pending.
Простая переписка продолжает работать; повторная отправка принятых сообщений
не является способом восстановления учёта.

## 6. Идентичность подсказки и слияние контактов

Backend этого этапа требует companion `fix/logic-metering-transport`: ReplyBox
передаёт `content_attributes.copilot.suggestion_request_id` в основном запросе
создания сообщения. Только первый текстовый сегмент одного ответа несёт ID.
Mapper уже передаёт content attributes; менять его не требуется. Схема → drain
старых writers → одновременный допуск нового backend и transport → preflight →
активация остаются отдельными воротами. Между drain и допуском нового кода
закрыть старые вкладки ReplyBox/сбросить старые cached drafts: подсказки,
сгенерированные до новой таблицы, нужно создать заново, без догадок по тексту.
Не активировать backend отдельно от companion и не допускать старые клиенты,
которые могут отправлять принятые подсказки без этого поля.

Сгенерированный draft сначала получает SQL identity, затем публикуется в Redis.
Хранятся только request/account/conversation/creator IDs и время, без текста.
Один SQL-путь проверяет исходную принадлежность и текущий ConversationPolicy;
основное сохранение Message не зависит от feedback или Redis. Изменённый текст
не меняет идентичность. Придуманный ID/чужая беседа/другой автор отклоняются.
Доступ к подсказкам в существующем UI персональный (latest key и cable stream
автора); новый межсотруднический handoff этим релизом не вводится.

Merge блокирует account PhoneIdentityLock до Contact/Message, сохраняет обе
истории до переноса бесед и удаления duplicate, затем пересчитывает общий
24ч/20 timeline. Manual merge, ReferenceMergeService и ChannelSync используют
один MergeAiUsageService. Outbox берёт тот же gate до Message lock; события
переносятся без изменения source keys. Разные accounts не объединяются. Клинический перенос ссылок
`PatientContactTransferService` сохраняет conversations и их metering на каждой
стороне отдельно (`merge_ai_usage: false`); общий телефон не объединяет окна.
Если две новые оплаченные истории после merge оказались одним окном, monthly
usage получает точную разницу по исходным месяцам; уже выставленные счета и
платежи этот код не переписывает. Legacy credits обеих сторон сохраняются,
включая одинаковые по времени seeds: одинаковые записи не дедуплицируются.
Откат: pause, сохранить SQL identities/events/pending, исправить код вперёд;
не удалять таблицу identities и не возвращать старые writers после активации.
