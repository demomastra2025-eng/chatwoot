# Откат миграций 20261004* (жизненный цикл CRM, Captain, напоминания)

Все миграции этой серии необратимы: `down` вызывает `ActiveRecord::IrreversibleMigration`.
Не запускайте `db:rollback` и `db:migrate:redo`. Откат релиза означает:
**старый образ + добавленная схема остаётся** (схема только расширяется).

## Миграции и порядок

| Версия | Что делает | Блокировки |
| --- | --- | --- |
| `20261004120000` | колонки `crm_tasks`, `crm_deals`, `crm_pipelines`, `crm_events`; записывает границы в `ar_internal_metadata` | `SET LOCAL lock_timeout = 5s`, до 5 повторов, по одной таблице |
| `20261004120100` | новые таблицы `crm_task_types`, `crm_task_outcomes`, `crm_stage_field_requirements`, `crm_stage_visits` без внешних ключей | только новые объекты |
| `20261004120200` | внешние ключи и CHECK как `NOT VALID` | `lock_timeout` 5 с, повторы |
| `20261004120250` | каталоги типов и результатов задач для аккаунтов, у которых их нет (имена равны системным кодам) | только новые строки |
| `20261004120300` | данные пачками по 5000 строк (пояс задач, `context_kind`, ссылки на каталог, `published_at` старых событий, оценочные визиты) | только строки |

## Если выкладка остановилась посреди серии

Сервисы при этом не переключены (`database preparation failed before rollout`), старый код работает
на уже расширенной схеме. Каждый шаг повторяем и сходится к одному состоянию:

1. Просто запустите выкладку снова (`rails db:chatwoot_prepare`): завершённые шаги ничего не меняют.
2. `PG::LockWaitTimeout` после 5 попыток: на таблице долго висит транзакция. Повторите вне часов нагрузки.
3. Недействительный индекс (оборванный `CREATE INDEX CONCURRENTLY`) перестраивается `REINDEX CONCURRENTLY`
   при следующем запуске; `NOT VALID` ключи и проверки доводит до `VALID` `20261004120500`.
4. Колонки, таблицы, индексы и `NOT VALID` проверки не мешают старому коду: он не знает о новых колонках,
   значения по умолчанию подходят его записям (`all_day = false`, `due_on` пуст, `reschedule_count = 0`, ...).

## Откат приложения после успешной выкладки

1. Верните предыдущий образ штатным откатом promotion-скрипта. Схему не трогайте.
2. Ничего не удаляйте: `DROP COLUMN`, `DROP TABLE` и `DROP INDEX` допустимы только отдельной проверенной
   задачей (contract-фаза), а не откатом. Расшифровки звонков и текст документов хранятся всегда.
3. События CRM, созданные новым кодом, уже имеют `published_at`: старый код его игнорирует.
4. Если потом снова выкатываете новый код, события, которые старый код записал во время отката, надо пометить
   опубликованными до запуска новых воркеров (старый код отправляет событие сразу при создании и
   `published_at` не ставит, повторная рассылка отправила бы их второй раз). Пачками по id:

   ```sql
   UPDATE crm_events SET published_at = created_at
   WHERE published_at IS NULL AND created_at BETWEEN '<начало отката>' AND '<момент новой выкладки>'
     AND id BETWEEN <от> AND <до>;
   ```

## Границы в `ar_internal_metadata` (не удалять)

- `crm_events_envelope_cutover`, `crm_tasks_schedule_cutover`: момент, когда колонки появились; эпоха
  (1970), если колонки уже были (DEV, линия aset). Строки старше границы считаются историей.
- `crm_tasks_schedule_backfilled`: часовые пояса задач заполняются один раз; повтор их не перезаписывает.
- `crm_events_legacy_publication_baseline`: граница, до которой `20261004193200` пометил события опубликованными.
  Повтор её не двигает. Если новый код уже публикует события, граница остаётся на момент появления колонки.

## Известное остаточное окно

Rollout идёт workers, второй web, первый web. Пока первый web ещё на старом образе, он создаёт события без
`published_at`, а уже обновлённые воркеры могут досылать такие события. Окно равно времени от конца
`db:chatwoot_prepare` до пересоздания первого web. Если для вас это недопустимо, перед рестартом воркеров
выполните тот же `UPDATE` (шаг 4 раздела об откате приложения) для событий, созданных после начала выкладки.
