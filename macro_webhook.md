# Логика обработки вебхука `estate.managerChanged`

## 1. Цель

Нужно обработать входящий `POST`-вебхук от MacroCRM при смене ответственного по заявке.

Проблема:

- в payload вебхука не приходит `manager_id`
- поэтому `manager_id` нужно добирать отдельным запросом в MacroCRM по `estate_id`

После получения `manager_id` нужно:

- если менеджер назначен, поменять ответственного по номеру телефона в нашей системе
- если менеджер пустой, снять ответственного по номеру телефона в нашей системе

## 2. Входящий вебхук

Метод:

```http
POST
```

Наш endpoint:

```text
/webhooks/macrocrm/:webhook_key/manager_changed
```

Где:

- `webhook_key` — публичный ключ вебхука для конкретного подключения MacroCRM
- `webhook_key` хранится в нашей интеграции как `integrations_hooks.reference_id`
- ключ генерируется OneLink при создании MacroCRM hook, показывается в настройках интеграции и вставляется в URL вебхука в MacroCRM

Это решение закрывает две проблемы сразу:

- вебхук однозначно привязывается к конкретному `Integrations::Hook`
- поиск по телефону выполняется уже строго внутри `hook.account`, а не по всей системе

Ожидаем принимать JSON такого вида:

```json
{
  "action": "estate.managerChanged",
  "time": 1774706531,
  "data": {
    "object": {
      "estate_id": 6841608,
      "client_phones": "+7.7719699769",
      "status": 10,
      "previous_status": 5,
      "updated_at": "2026-03-28 18:53:43"
    },
    "event": "estate.managerChanged"
  }
}
```

Обрабатывать нужно только события:

```text
action == "estate.managerChanged"
```

или

```text
data.event == "estate.managerChanged"
```

Если событие другое, обработку нужно завершать без действий.

## 3. Что брать из вебхука

Из входящего payload нужно извлекать:

- `estate_id = body.data.object.estate_id`
- `phoneRaw = body.data.object.client_phones`
- `status = body.data.object.status`
- `previous_status = body.data.object.previous_status`
- `updated_at = body.data.object.updated_at`

Этого достаточно для запуска всей логики.

Дополнительно фиксируем назначение полей:

- `status` используется в основном запросе `estateBuy/list`
- `previous_status` используется только для логирования
- `updated_at` используется для защиты от устаревших вебхуков

## 4. Нормализация телефона

Телефон из вебхука приходит в формате:

```text
+7.7719699769
```

Его нужно нормализовать в формат:

```text
+77719699769
```

Правило:

- оставить только цифры
- затем добавить ведущий `+`

Пример:

```text
+7.7055606219 -> +77055606219
+7 771 969 9769 -> +77719699769
```

Функция:

```js
function normalizePhone(phone) {
  if (!phone) return '';
  const digits = String(phone).replace(/\D/g, '');
  if (!digits) return '';
  return '+' + digits;
}
```

## 5. Основной запрос в MacroCRM

### 5.1. Зачем нужен запрос

Сам вебхук не содержит `manager_id`, поэтому его нужно получить по `estate_id`.

Основной способ:

```http
POST /estateBuy/list
```

### 5.2. Базовый запрос

Request:

```json
{
  "ids": [6841608],
  "statuses": [10]
}
```

Где:

- `6841608` — это `estate_id` из вебхука
- `10` — это `status` из вебхука

### 5.3. Заголовки

Использовать стандартные заголовки MacroCRM:

```http
Authorization: Bearer <MACRO_TOKEN>
AppId: <APP_ID>
Content-Type: application/json
```

### 5.4. Что брать из ответа

Ожидаемая структура ответа:

```json
{
  "success": true,
  "status": "ok",
  "buys": [
    {
      "id": 6841608,
      "status": 10,
      "contact": {
        "id": 6084192,
        "phones": ["+7 771 969 9769"]
      },
      "manager": {
        "id": 78731,
        "name": "Мереке Мираз"
      }
    }
  ]
}
```

Нужные поля:

- `buys[0].id`
- `buys[0].manager.id`
- `buys[0].contact.phones`

Правило по телефону:

- основной источник телефона для поиска чата: `body.data.object.client_phones`
- если после нормализации он пустой, используем первый телефон из `buys[0].contact.phones`
- если и там телефона нет, обработка завершается без действий, но с логом

## 6. Как трактовать менеджера

### 6.1. Если менеджер назначен

Если:

```text
manager.id != null
manager.id != 0
```

то:

- считаем, что в MacroCRM у заявки есть ответственный
- по таблице маппинга находим соответствующего ответственного в нашей системе
- назначаем его по номеру телефона

### 6.2. Если менеджер пустой

Если:

```text
manager.id == null
```

или

```text
manager.id == 0
```

то:

- считаем, что ответственный в MacroCRM снят
- в нашей системе по этому номеру телефона нужно снять ответственного

Это обязательное правило.

## 7. Действия в нашей системе

### 7.1. Если менеджер есть

Нужно выполнить:

```text
setResponsibleByPhone(normalizedPhone, localResponsibleId)
```

Где:

- `normalizedPhone` — нормализованный телефон клиента
- `localResponsibleId` — внутренний id ответственного в нашей системе

Маппинг:

```text
macroManagerId -> localResponsibleId
```

Пример:

```json
[
  { "user_id": 42, "macro_manager_id": 78731 },
  { "user_id": 17, "macro_manager_id": 79755 },
  { "user_id": 61, "macro_manager_id": 79264 }
]
```

Правило разрешения маппинга:

1. сначала ищем `macro_manager_id` в `hook.settings.manager_mappings`
2. если явного маппинга нет, ищем пользователя по `user.custom_attributes.macrocrm_manager_id`
3. использовать можно только назначаемого локального агента

Назначаемым агентом считаем только такого пользователя, который:

- принадлежит этому `account`
- имеет роль `agent`
- состоит в inbox, где находится целевой чат
- если у чата есть `team`, входит и в эту `team`

Если `manager_id > 0`, но локальный агент не найден или не может быть назначен:

- не снимаем текущего ответственного
- не назначаем администратора
- пишем warning в лог
- возвращаем HTTP `200`

### 7.2. Если менеджер пустой

Нужно выполнить:

```text
removeResponsibleByPhone(normalizedPhone)
```

То есть ответственный в нашей системе должен быть снят.

### 7.3. Что именно значит "по номеру телефона"

Операции `setResponsibleByPhone(...)` и `removeResponsibleByPhone(...)` в нашей реализации работают не по всем чатам номера, а по одному целевому чату.

Правило выбора целевого чата:

1. ищем только внутри `hook.account`
2. рассматриваем только WhatsApp и Twilio WhatsApp conversations
3. кандидатами считаем conversations, у которых совпал хотя бы один из признаков:
   - `contacts.phone_number == normalizedPhone`
   - нормализованный `contact_inboxes.source_id` совпадает с `normalizedPhone`
4. из кандидатов сначала берём последний чат со статусом не `resolved`, сортировка по `last_activity_at DESC`
5. если открытых/ожидающих чатов нет, берём вообще последний чат по `last_activity_at DESC`
6. если чата нет, пишем log и завершаем обработку без действий

Итог:

- один вебхук меняет одного ответственного у одного наиболее релевантного чата
- массовое переприсваивание всех разговоров по номеру не делаем

## 8. Резервная логика, если `estateBuy/list` не вернул заявку

Основной запрос должен быть через `POST /estateBuy/list`.

Но если по какой-либо причине:

- `buys` пустой
- сделка не нашлась
- ответ неполный

нужно использовать резервную схему:

### Шаг 1. Найти контакт по телефону

```http
POST /contacts/find
```

Request:

```json
{
  "phone": "+77719699769"
}
```

### Шаг 2. Найти все сделки контакта

```http
POST /estateBuy/find
```

Request:

```json
{
  "contacts_id": 6084192
}
```

### Шаг 3. Найти нужную сделку в массиве

Нужно выбрать сделку, у которой:

```text
buy.id == estate_id
```

### Шаг 4. Взять `manager_id`

В резервном сценарии брать:

```text
buy.manager_id
```

Если:

- `manager_id > 0` — назначить ответственного
- `manager_id == 0` — снять ответственного

## 9. Полная последовательность действий

```text
1. Принять POST-вебхук
2. Проверить, что action/event == estate.managerChanged
3. Извлечь estate_id, client_phones, status, previous_status
4. Нормализовать телефон
5. Вызвать POST /estateBuy/list с ids=[estate_id], statuses=[status]
6. Если заявка найдена:
      6.1. взять buys[0].manager.id
      6.2. если manager.id > 0:
              найти локального assignable agent по manager_mappings/custom_attributes
              назначить ответственного в выбранном целевом чате
      6.3. если manager.id == null или manager.id == 0:
              снять ответственного в выбранном целевом чате
7. Если заявка не найдена:
      7.1. вызвать POST /contacts/find по телефону
      7.2. вызвать POST /estateBuy/find по contacts_id
      7.3. найти сделку по estate_id
      7.4. взять manager_id
      7.5. если manager_id > 0:
              найти локального assignable agent по manager_mappings/custom_attributes
              назначить ответственного в выбранном целевом чате
      7.6. если manager_id == 0:
              снять ответственного в выбранном целевом чате
8. Если локальный маппинг не найден или чат не найден:
      8.1. записать warning в лог
      8.2. не менять данные
9. Записать результат в лог
10. Вернуть HTTP 200
```

## 10. Важное замечание по вебхукам

По официальной документации MacroCRM:

- система не делает повторную отправку вебхука, если принимающий сервер не ответил `200 OK`

Поэтому:

- нужно обязательно завершать обработку ответом `200`
- если произошла внутренняя ошибка, ее нужно логировать отдельно

### 10.1. Правило ответа наружу

Во всех следующих случаях наружу всё равно возвращается HTTP `200 OK`:

- пришёл не тот `action/event`
- `webhook_key` не найден
- не удалось нормализовать телефон
- не найдена сделка
- не найден чат в нашей системе
- не найден локальный маппинг менеджера
- произошла внутренняя ошибка

Во всех этих случаях различается только внутренний лог и факт применения или неприменения изменений.

### 10.2. Защита от устаревших вебхуков

Поле `updated_at` используем как anti-stale защиту.

Правило:

- в `conversation.custom_attributes['macrocrm_manager_changed_at']` сохраняем timestamp последнего успешно обработанного вебхука MacroCRM
- если новый вебхук пришёл с `updated_at`, который меньше или равен уже сохранённому значению, считаем его устаревшим
- устаревший вебхук не меняет ответственного, только логируется

Это нужно, чтобы более старое событие не перетёрло более новое назначение.

## 11. Практически проверенные кейсы

### Кейс 1. У заявки менеджер пустой

Проверенный пример:

- `estate_id = 6641007`
- `manager.id = null` в `estateBuy/list`
- `manager_id = 0` в `estateBuy/find`

Вывод:

- в нашей системе нужно снять ответственного

### Кейс 2. У заявки менеджер назначен

Проверенный пример:

- `estate_id = 6841608`
- `manager.id = 78731` в `estateBuy/list`
- `manager_id = 78731` в `estateBuy/find`

Вывод:

- в нашей системе нужно назначить ответственного, соответствующего `macroManagerId = 78731`

## 12. Итоговое правило

Если по вебхуку `estate.managerChanged` у заявки в MacroCRM:

- есть `manager.id` или `manager_id > 0` — назначить соответствующего ответственного в нашей системе
- `manager.id == null` или `manager_id == 0` — снять ответственного в нашей системе
