# Восстановление существующего billing pipeline

Изменение исходников не включает автобиллинг, провайдеров или фоновые задачи на стендах.
Общие payer/UsageLedger, перенос данных, цены и места находятся вне этого механизма.

`Invoice.metadata.completion_v1` владеет PDF, BCC-регистрацией, локальной ссылкой оплаты,
уведомлением о счёте и внешними документами. `PaymentEvent.metadata.completion_v1` владеет
подтверждением оплаты и задачей проверки. Суммы, финансовая запись и продление фиксируются
только первой финансовой транзакцией. Найденная запись продолжает разрешённые незавершённые
шаги; повтор не рассчитывает сумму и не продлевает срок второй раз.

Канонические target и реквизиты документа сохраняются в Invoice при создании. Event хранит
ссылку на Invoice и срок из settlement. Текущий Profile не подменяет исторические реквизиты
или адресата. Первоначальный `notify:false` навсегда оставляет `invoice_issued` в `skipped`.

Каждый шаг содержит `operation_key`, `input_digest` исходного контекста и состояние:

| Состояние | Смысл |
| --- | --- |
| `pending` | Разрешённый шаг ещё не завершён. |
| `running` | Короткая SQL-транзакция выдала token; работа выполняется вне неё. |
| `completed` | Записан конкретный receipt: blob ID, Message ID, task ID или внешний document ID. |
| `blocked` | Известное препятствие до отправки: конфигурация, отсутствующий PDF или изменённый target. |
| `needs_review` | Неизвестный внешний исход, просроченный внешний claim либо недоказанные старые данные. Автоповтора POST нет. |
| `skipped` | Шаг не был разрешён исходным намерением. |

Внешний claim старше пяти минут становится `needs_review`. Это срок обнаружения зависшей
операции, а не разрешение повторить её. Поздний ответ со старым token не перезаписывает
новый результат. Клиенты BCC/ЭДО/ЭСФ не объявляются exactly-once: доказанной сверки или
провайдерского idempotency key здесь нет. HTTP timeout, невалидный ответ и отсутствующий
receipt требуют проверки. Доказанное отсутствие конфигурации до POST остаётся `blocked`.
Существующий внешний ID является receipt и не разрешает другой недоказанный внешний шаг.

PDF render/upload выполняются вне финансовой SQL-транзакции. Готовый blob и checkpoint
прикрепляются под Invoice lock; проигравший подготовленный blob удаляется вне locks.
Устаревший PDF claim можно забрать, поскольку подготовка обратима. При жёстком завершении
процесса может остаться непривязанный blob; второй активной attachment не создаётся.

Message и его marker сохраняются одной транзакцией. Message ID подтверждает создание,
а не доставку провайдером. Обычные Message callbacks выполняются после commit. Ошибка
доставки не разрешает создавать новый Message. Отсутствующий, чужой или изменённый billing
conversation блокирует уведомление; автоматически выбрать другой диалог нельзя.

Порядок блокировок: identity → Contact по ID → все Account по ID (`FOR NO KEY UPDATE`) →
Invoice → Event → Profile. Все обычные Profile `save!`/`update!` берут Account перед
неявным Profile UPDATE. Старое зеркало срока в Account сохраняется. SQL helper не берёт
новых Contact/Account из-под Invoice/Event. Внешний IO внутри открытой SQL-транзакции запрещён.

Существующий upcoming job возобновляет managed Invoice/Event по ограниченному на старте
диапазону ID независимо от возраста. Автоматически создавать новый счёт можно только за
период `today..today+5`; recurring job создаёт новый счёт только за `today`. Общий scope
Profile и повторная проверка под Account lock закрывают гонку с изменением Profile.
Прошлые неизвестные периоды пропускаются. Отменённый период не перевыставляется автоматически;
существующий явный ручной вызов генератора сохраняет прежнее поведение.

Записи без checkpoints не получают разрешение на массовую рассылку или POST. Старый
`notified` либо последние audit entries не доказывают Message ID. Недостающий BIN/договор
не восстанавливается из текущего Profile. Для снятия `needs_review` нужны отдельная сверка,
конкретный исход/receipt и разрешённое решение; универсального «сбросить claim и повторить» нет.

Проверки используют только собственную пустую тестовую PostgreSQL БД и Redis namespace,
синтетические реквизиты и WebMock с запретом внешних соединений. Независимое ревью и
отдельный runtime/data/release допуск обязательны до включения на стендах.
